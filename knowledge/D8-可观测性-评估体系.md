## D8.1 Trace 系统：TraceContext 与 TraceCollector 的采集与关联设计

### 设计动机

RAG 系统的"黑盒"问题：为什么召回了这些文档？Rerank 前后排名如何变化？哪一步最慢？

Trace 系统让每次 Query/Ingestion 都有完整的链路记录，可在 Dashboard 中逐阶段回溯。

### TraceContext 数据结构

```python
class TraceContext:
    trace_id: str          # UUID4，全局唯一
    trace_type: str        # "query" 或 "ingestion"
    started_at: datetime   # 链路开始时间（UTC ISO）
    finished_at: datetime  # 链路结束时间
    metadata: dict         # 链路级元数据（user_query / source_path / collection）
    stages: List[SpanRecord]  # 各阶段记录列表
```

### 两种记录方式

**显式记录（IngestionPipeline 用）：**
```python
t0 = time.monotonic()
chunks = chunker.split(document)
trace.record_stage("split",
    duration_ms=(time.monotonic()-t0)*1000,
    method="recursive",
    chunk_count=len(chunks))
```

**上下文管理器（自动计时）：**
```python
with trace.span("rerank") as span:
    span.data["backend"] = "cross_encoder"
    results = reranker.rerank(query, candidates)
    span.data["result_count"] = len(results)
# 退出 with 块自动记录 duration_ms
```

### TraceContext.to_dict() 输出格式

```json
{
  "trace_id": "550e8400-...",
  "trace_type": "query",
  "started_at": "2026-07-07T12:00:00Z",
  "finished_at": "2026-07-07T12:00:00.850Z",
  "total_elapsed_ms": 850.12,
  "metadata": {"user_query": "如何配置 Azure？", "collection": "default"},
  "stages": [
    {"stage": "dense_retrieval", "duration_ms": 210.5, "result_count": 20, "method": "dense"},
    {"stage": "sparse_retrieval", "duration_ms": 15.3, "result_count": 18, "method": "bm25"},
    {"stage": "fusion", "duration_ms": 2.1, "algorithm": "rrf", "result_count": 10},
    {"stage": "rerank", "duration_ms": 0.1, "backend": "none", "fallback": false}
  ]
}
```

### TraceCollector 持久化

```python
class TraceCollector:
    def collect(self, trace: TraceContext) -> None:
        trace.finish()
        line = json.dumps(trace.to_dict(), ensure_ascii=False)
        # 追加写入 logs/traces.jsonl（每行一条完整 trace）
        with open("logs/traces.jsonl", "a", encoding="utf-8") as f:
            f.write(line + "\n")
```

**低侵入性设计**：Pipeline 结束时 `global_collector.collect(trace)`，失败不影响主流程（`try/except` 吞掉 collector 异常）。

## D8.3 评估指标体系：Recall / Precision / MRR 等核心指标

### 为什么要量化评估

"凭感觉"调优是 RAG 系统最常见的反模式。改了 chunk_size 或换了 Reranker，必须有量化分数才能判断效果好还是差。

### 核心检索指标

| 指标 | 公式/说明 | 含义 |
|------|----------|------|
| **Hit Rate@K** | 命中数 / 总查询数 | Top-K 结果中至少有一个正确答案的比例 |
| **MRR@K** | `1/N * Σ 1/rank_i` | 正确答案的平均倒数排名，越高表示正确答案越靠前 |
| **NDCG@K** | 归一化折现累积增益 | 综合考虑相关度和排名位置 |

### Ragas 框架指标（生成质量）

| 指标 | 含义 | 目标阈值 |
|------|------|---------|
| **Faithfulness** | 生成答案与召回文档的一致性（是否有幻觉） | ≥ 0.9 |
| **Answer Relevancy** | 生成答案与用户问题的相关性 | ≥ 0.85 |
| **Context Precision** | 召回文档中有用内容的比例 | ≥ 0.8 |
| **Context Recall** | 相关内容的召回完整性 | ≥ 0.85 |

## D8.4 评估框架：CompositeEvaluator / LocalEvaluator / RagasEvaluator

### BaseEvaluator 接口

```python
class BaseEvaluator(ABC):
    @abstractmethod
    def evaluate(
        self,
        query: str,
        retrieved_chunks: List[dict],
        generated_answer: str,
        ground_truth: Optional[str] = None,
    ) -> dict:
        """返回标准化指标字典，如 {"hit_rate": 0.9, "mrr": 0.82}"""
        pass
```

### 可插拔评估后端

```python
# 配置
evaluation:
  backends: [custom]    # 可改为 [ragas, custom] 并行跑两套

# CompositeEvaluator 并行执行所有后端并合并结果
class CompositeEvaluator:
    def __init__(self, evaluators: List[BaseEvaluator]): ...
    def evaluate(self, ...) -> dict:
        results = {}
        for evaluator in self._evaluators:
            results.update(evaluator.evaluate(...))  # 合并 metrics
        return results
```

### 黄金测试集（Golden Test Set）

```json
{
  "test_cases": [
    {
      "query": "如何配置 Azure OpenAI？",
      "expected_chunk_ids": ["chunk_abc_001", "chunk_abc_002"],
      "expected_sources": ["config_guide.pdf"]
    }
  ]
}
```

**EvalRunner 工作流**：
1. 加载 `tests/fixtures/golden_test_set.json`
2. 对每条 test_case 执行 `HybridSearch.search(query)`
3. 比对召回结果与 expected_chunk_ids
4. 计算 Hit Rate / MRR / NDCG

## D8.5 日志系统：Logger 设计、日志分级与调试支持

### 结构化日志设计

```python
# src/observability/logger.py
class JSONFormatter(logging.Formatter):
    def format(self, record) -> str:
        log_obj = {
            "ts": datetime.utcnow().isoformat(),
            "level": record.levelname,
            "module": record.name,
            "msg": record.getMessage(),
        }
        return json.dumps(log_obj, ensure_ascii=False)

def get_logger(name: str) -> logging.Logger:
    logger = logging.getLogger(name)
    handler = logging.StreamHandler(sys.stderr)   # 关键：走 stderr！
    handler.setFormatter(JSONFormatter())
    logger.addHandler(handler)
    return logger
```

**`stderr` 的强制约束**：MCP Server 的 `stdout` 只能有 JSON-RPC 消息。任何混入 `stdout` 的日志都会导致 Client 解析失败。所有日志必须走 `stderr`。

### Trace 持久化日志

```python
def write_trace(trace_dict: dict) -> None:
    log_file = Path("logs/traces.jsonl")
    log_file.parent.mkdir(exist_ok=True)
    with open(log_file, "a", encoding="utf-8") as f:
        f.write(json.dumps(trace_dict, ensure_ascii=False) + "\n")
```

**JSON Lines 格式（.jsonl）** 的优点：
- 每行独立：部分行损坏不影响其他行的解析
- 流式追加：不需要读全文件再写回
- 工具友好：可以用 `jq` 命令行直接查询过滤

## D8.1 Trace System: TraceContext and TraceCollector Design

### Motivation

The RAG "black box" problem: why were these chunks retrieved? How did rankings change before/after reranking? Which stage was slowest? The Trace system gives every Query/Ingestion run a complete chain record reviewable stage-by-stage in the Dashboard.

### TraceContext Data Structure

```python
class TraceContext:
    trace_id: str          # UUID4, globally unique
    trace_type: str        # "query" or "ingestion"
    started_at: datetime   # UTC ISO wall-clock time
    metadata: dict         # chain-level context (user_query / source_path / collection)
    stages: List[SpanRecord]  # per-stage records
```

### Two Recording Styles

**Explicit recording** (used by IngestionPipeline):
```python
t0 = time.monotonic()
chunks = chunker.split(document)
trace.record_stage("split", duration_ms=(time.monotonic()-t0)*1000, chunk_count=len(chunks))
```

**Context manager** (auto-timing):
```python
with trace.span("rerank") as span:
    span.data["backend"] = "cross_encoder"
    results = reranker.rerank(query, candidates)
    span.data["result_count"] = len(results)
# duration_ms is recorded automatically on exit
```

### `to_dict()` Output

```json
{
  "trace_id": "550e8400-...",
  "trace_type": "query",
  "total_elapsed_ms": 850.12,
  "stages": [
    {"stage": "dense_retrieval", "duration_ms": 210.5, "result_count": 20, "method": "dense"},
    {"stage": "sparse_retrieval", "duration_ms": 15.3,  "result_count": 18, "method": "bm25"},
    {"stage": "fusion",           "duration_ms": 2.1,   "algorithm": "rrf", "result_count": 10},
    {"stage": "rerank",           "duration_ms": 0.1,   "backend": "none",  "fallback": false}
  ]
}
```

**Low-intrusiveness**: `TraceCollector.collect()` is called at the end of the pipeline inside a `try/except` — a collector failure never affects the main flow.

## D8.3 Evaluation Metrics: Recall / MRR / Ragas Indicators

### Retrieval Metrics

| Metric | Formula / Description | Target |
|--------|----------------------|--------|
| **Hit Rate@K** | queries with ≥1 correct result in Top-K / total queries | ≥ 0.90 |
| **MRR@K** | `1/N · Σ 1/rank_i` where rank_i is the position of the first correct result | ≥ 0.80 |
| **NDCG@K** | normalized discounted cumulative gain — accounts for both relevance and position | ≥ 0.85 |

### Ragas Generation Quality Metrics

| Metric | Meaning | Target |
|--------|---------|--------|
| **Faithfulness** | Is the generated answer grounded in retrieved chunks? (hallucination detection) | ≥ 0.90 |
| **Answer Relevancy** | Does the answer address the user's question? | ≥ 0.85 |
| **Context Precision** | What fraction of retrieved content is actually useful? | ≥ 0.80 |

## D8.4 Evaluation Framework: CompositeEvaluator / LocalEvaluator / RagasEvaluator

```python
class BaseEvaluator(ABC):
    @abstractmethod
    def evaluate(self, query, retrieved_chunks, generated_answer, ground_truth=None) -> dict:
        """Returns a normalized metrics dict, e.g. {"hit_rate": 0.9, "mrr": 0.82}"""
```

**CompositeEvaluator** runs all configured backends in parallel and merges results:
```yaml
evaluation:
  backends: [ragas, custom]   # both run; metrics are merged into one report
```

**Golden Test Set** (`tests/fixtures/golden_test_set.json`):
```json
{"test_cases": [{"query": "...", "expected_chunk_ids": ["chunk_abc_001"], "expected_sources": ["guide.pdf"]}]}
```

**EvalRunner** feeds the golden set through `HybridSearch`, compares results against ground truth, and computes Hit Rate / MRR / NDCG per query.

## D8.5 Logging System: JSONFormatter, Log Levels, Debug Support

```python
class JSONFormatter(logging.Formatter):
    def format(self, record) -> str:
        return json.dumps({"ts": "...", "level": record.levelname,
                           "module": record.name, "msg": record.getMessage()})

def get_logger(name: str) -> logging.Logger:
    handler = logging.StreamHandler(sys.stderr)   # MUST be stderr — stdout is reserved for MCP
    handler.setFormatter(JSONFormatter())
    ...
```

**The stderr constraint**: anything written to stdout that is not valid JSON-RPC will crash the MCP client. All logging is forced to stderr at the framework level.

**JSON Lines format** (`.jsonl`) advantages:
- One record per line — a corrupt line doesn't break parsing of others.
- Append-only writes — no need to read the whole file before writing.
- Tooling-friendly — query with `jq`, `grep`, or the Dashboard's TraceService.
